# Network Constraints & Break Drills (Week 2, Day 5)

| Constraint | Where I Hit It | Symptom | Layer | Fix | Enterprise Implication |
|---|---|---|---|---|---|
| Storage Private DNS zone unlinked from VNet (`privatelink.blob.core.windows.net`) | Storage Break Drill (API SSH → `bulk-player-enrollment`) | `HTTP 403 remote=20.60.84.33` (resolved public IP instead of `10.10.1.5`) | DNS | Re-link Private DNS zone to VNet via Bicep (`virtualNetworkLinks`); wait >10s TTL | A `403` on a private PaaS service is often a **DNS** fault, not RBAC—always inspect resolved IP first (`remote_ip` / `getent hosts`). |
| Storage `publicNetworkAccess: Disabled` blocks all public data-plane clients | Laptop `az storage blob list`, Portal Storage Browser, client SAS upload | `403 AuthorizationFailure` (network rules blocking public access) | Service setting | Keep public access off; run admin/data-plane tools from VNet-connected runner/jumpbox, or proxy client uploads instead of direct public SAS | Portal Storage Browser runs in your browser (public IP), not via Azure backbone; direct-to-blob public SAS conflicts with `publicNetworkAccess: Disabled`. |
| Container-scoped least-privilege RBAC vs network `403` | API SSH → `event-docs` vs `bulk-player-enrollment` | `HTTP 403 remote=10.10.1.5` on `event-docs`; `HTTP 200 remote=10.10.1.5` on `bulk-player-enrollment` | Identity | Expected by design (API owns `bulk-player-enrollment`; Functions owns `event-docs`) | `remote_ip` instantly disambiguates `403`: public IP = DNS/firewall (`Service setting`/`DNS`), `10.x` IP = `Identity`/RBAC. |
| `Microsoft.Web/sites@2024-11-01` deprecated `vnetRouteAllEnabled` | VNet Integration deploy verification (`az webapp show`) | `vnetRouteAllEnabled` remained `False` after Bicep deploy | Routing (IaC) | Replace `vnetRouteAllEnabled` with `outboundVnetRouting: { applicationTraffic: true }` on API, Worker, Functions, and all staging slots | API schema changes can silently drop security routing flags; verify effective live state on every slot (VNet Integration does not swap across slots). |
| NSG denies TCP `1433` on `snet-pe` (`privateEndpointNetworkPolicies: Enabled`) | SQL Break Drill (`allow-appsvc-sql` deleted from `nsg-snet-pe`) | `getent hosts` still resolved `10.10.1.7`, but TCP `1433` & `/health/ready` timed out / failed connection establishment (NOT `403`) | Filtering | Restore `allow-appsvc-sql` via Bicep (`nsg-snet-pe`) | NSGs drop SYN silently (timeout), unlike DNS fallback (public IP + `403`/denied). `privateEndpointNetworkPolicies: Enabled` is required or NSGs are silently bypassed on PEs. |
| SQL `publicNetworkAccess: Disabled` blocks laptop & GitHub-hosted `efbundle` | Laptop Entra `SqlConnection` + `Test-NetConnection -Port 1433` | `Test-NetConnection` passed against shared public gateway `20.192.43.160:1433`, then TDS login failed (`Deny Public Network Access`) | Service setting | Remove all 44 `sqlAllowedIps` (rebuild gap 1); adopt Option A (`snet-aci` `10.10.1.128/25` + `nsg-snet-pe` `1433` allow for VNet container/runner) | TCP port-open checks don't prove PaaS access; once Storage and SQL are both private, CI migrations/grants must run from inside the VNet (self-hosted runner or ephemeral container). |
| Azure SQL Private Link connection policy (`Default`/Proxy vs `Redirect`) + FQDN rule | SQL PE setup (`conn-policy show` = `Default`) | Works on TCP `1433` only when `Default` (falls back to Proxy); direct `10.10.1.7` fails TLS/SNI by design | Routing / Service setting | Always connect via `<server>.database.windows.net`; keep `Default`/`Proxy` for `1433`-only NSGs, or open TCP `1433–65535` if enabling `Redirect` | Flipping SQL to `Redirect` without widening PE NSGs to `1433–65535` causes logins to pass (`1433`) and queries to time out. |
| OpenAI `publicNetworkAccess: Disabled` blocks laptop & AI Foundry Studio | Laptop PowerShell + Azure AI Foundry Playground (`oai-azurelab-dev-sin-jyqvnq`) | `HTTP 403` on PowerShell and Foundry Playground (`400` banner + `403` public access disabled) | Service setting | Keep public access disabled; run evals/tools from VNet runner or jumpbox; apps reach `10.10.1.8` over cross-region PE (`centralindia` → `southindia`) | Browser-based Foundry Studio / OpenAI Playground calls `*.openai.azure.com` from the user's public IP, just like Storage Browser and SQL Query Editor. |
| Missing `A` record inside a **linked** Private DNS zone (`privatelink.openai.azure.com`) | OpenAI Break Drill (deleted PE `dns-zone-group` while VNet link stayed active) | `NXDOMAIN` / `Could not resolve host` (NO fallback to public IP `20.192.153.164`) | DNS | Restore PE `privateDnsZoneGroups` via Bicep so the `A` record (`10.10.1.8`) is recreated | A linked `privatelink.*` zone is **authoritative** in the VNet: an empty/missing `A` record blackholes all lookups (`NXDOMAIN`) instead of falling back to public DNS—big hub-and-spoke hazard. |
| Wrong Private DNS zone name (e.g. `privatelink.cognitiveservices.azure.com` for `*.openai.azure.com`) | DNS drill comparison (OpenAI vs multi-service Foundry) | Falls back to public IP (`20.192.153.164`) → `HTTP 403` (identical to unlinked zone) | DNS | Match exact zone to FQDN (`privatelink.openai.azure.com` for `kind: OpenAI`; add `cognitiveservices` + `services.ai` for multi-service `AIServices`) | Multi-service Foundry PE NICs emit FQDNs across up to 3 zones; missing one zone causes silent public fallback + `403` on only that API surface. |
| Stale DNS cache / pooled HTTP connections after Private DNS change | Post-fix recovery window (`Ttl = 10` seconds on Private DNS `A` records) | App keeps hitting old public IP (`403`) or cached `NXDOMAIN` briefly after DNS fix | DNS (client cache) | Wait >10s TTL (or up to 2 min for `IHttpClientFactory` handler rotation / `PooledConnectionLifetime`); restart app for immediate flush | Long-lived `HttpClient` sockets ignore DNS TTL changes; always use `IHttpClientFactory` or set `PooledConnectionLifetime` on `SocketsHttpHandler`. |
| Rejected Private Endpoint approval (`srch-azurelab-dev-cin-jyqvnq`) | AI Search Break Drill (`private-endpoint-connection update --status Rejected`) | `10.10.1.9` still resolved in DNS, then `curl` hung and timed out (`Connection timed out after 10003 ms`, `HTTP 000`) | Service setting | Delete the terminal rejected PE (`az network private-endpoint delete`) and recreate via Bicep | Rejected/Pending PEs drop packets silently at the Private Link fabric—identical client symptom to an NSG drop (`10.x` + timeout); always check BOTH NSG and PE connection state. Rejections are terminal. |
| AI Search `publicNetworkAccess: 'disabled'` (lowercase) blocks laptop & Search Explorer | Laptop `AzureLab.SearchTool ensure-index` | `HTTP 403` from laptop; `HTTP 200 remote=10.10.1.9` from API SSH | Service setting | Run index schema creation (`ensure-index`) before lockdown or from a VNet runner; keep `publicNetworkAccess: 'disabled'` at rest | Search uses lowercase `'enabled' | 'disabled'` in ARM; deploy-time schema/re-index jobs need a VNet runner once locked down. |
| AI Search inbound PE vs outbound Shared Private Link tier split | AI Search PE setup (`skuName: 'basic'`) | Inbound PE works on `Basic` (`10.10.1.9`); outbound pull-indexers cannot use inbound PE | Service setting (SKU) | Use `Basic`+ for push/app-driven RAG (`IDocumentVectorStore`); upgrade to `Standard`+ if using outbound pull-indexers with Shared Private Link | Inbound PE only secures callers hitting Search; Search calling Storage/SQL/OpenAI via pull indexers requires outbound Shared Private Link (`Standard`+). |
| Functions polling Blob Trigger stalls after Storage DNS / `403` outage | Private Ingestion E2E (`day5-private-badge.png` uploaded over `10.10.1.5`) | `PUT 201` succeeded, but `EventDocumentFunction` did not fire until `az functionapp restart` | DNS / Service setting (host listener backoff) | Restart `func-azurelab-dev-cin-jyqvnq` after Storage PE/DNS changes so `AzureWebJobsStorage` re-initializes listeners over `10.10.1.4/.5/.6` | After any Storage Private DNS or firewall cutover, restart Function Apps (or use Event Grid blob triggers) so backed-off storage listeners recover immediately. |
| App Service `outboundVnetRouting` (`applicationTraffic` vs `allTraffic`) | Step 7 Outbound Routing Check (`Microsoft.Web/sites@2024-11-01`) | `applicationTraffic: true`, while `imagePullTraffic`, `contentShareTraffic`, `backupRestoreTraffic`, `managedIdentityTraffic` remain `false` | Routing | Keep `applicationTraffic: true` for standard PaaS egress; if setting `allTraffic: true` behind a hub Firewall/UDR `0.0.0.0/0` or `defaultOutboundAccess: false`, provide NAT Gateway/Firewall rules for MCR, Entra, Service Bus, and App Insights | Forcing `allTraffic: true` into a locked-down subnet without explicit egress rules breaks container image pulls, MI token acquisition, and telemetry. |
